# Контекст, сжатие и восстановление

## Основной принцип

Контекст модели — рабочий набор, а не единственное хранилище проекта. Важные
решения и ограничения сохраняются в графе, текущая работа — в checkpoint,
точные подробности — в оригиналах и архивах. Сжатие меняет то, что отправляется
модели, но не удаляет эти записи.

Краткая сводка модели по своей природе может упустить смысловой нюанс.
«Без потери» здесь обеспечивается для сохранённых оригиналов и версий:
их можно прочитать снова. Автоматически доказать, что модель правильно выбрала
всё существенное, нельзя; перед действием, зависящим от детали, агент проверяет
точный источник. Неподтверждённые сведения остаются неизвестными.

## Три уровня памяти

| Уровень | Что сохраняется | Когда загружается |
|---|---|---|
| Архитектурная память | Граф, ограничения, решения, основания, свидетельства, предложения и ревизии | Свежий ограниченный контекст перед каждым обращением к модели; подробный узел по ID |
| Операционный checkpoint | Цель, требования, решения, неизвестности, текущая работа, следующий шаг, ссылки | Всегда в автоматической вставке; историческая версия по запросу |
| Точные подробности | Крупные MCP-ответы и доступный transcript перед сжатием | Только нужные страницы/совпадения по `detail_id` |

Граф находится в `.architecture/architecture.sqlite`. Операционная память —
в `.architecture/architecture.context.sqlite`. Архивы неизменяемы, адресуются
SHA-256 содержимого и сохраняют связи с сессией/типом записи. Старые версии
checkpoint остаются доступны. Автоматического удаления архивов нет.

## Что нельзя терять при сжатии

1. Цель пользователя, последние поправки, обязательные требования и ограничения.
2. Принятые решения, основания, отвергнутые варианты, когда они существенны,
   и условия пересмотра. Принятый риск не превращается в техническую гарантию.
3. Что сделано и реально проверено; что ещё не сделано; отрицательные результаты,
   блокеры и вопросы без ответа.
4. Незавершённые задания, следующий шаг, активные фоновые действия и ссылки
   на результаты помощников.
5. ID узлов, предложений и свидетельств, ревизии, состояние рассмотрения diff,
   пути файлов и ID архивов. Предложение не называется согласованным без записи ядра.

Политика передаётся в compaction hook. Перед завершением содержательного хода
архитектор обновляет checkpoint через `save_checkpoint(expected_version, checkpoint)`.
Поля: `objective` — строка; `requirements`, `decisions`, `open_questions`,
`in_progress`, `next_actions`, `references` — списки строк. Размер до 6000 байт
UTF-8; большие подробности выносятся в источники, а не вычёркиваются из требований.
Контроль версии отклоняет устаревшее обновление параллельной сессии.

Checkpoint — сообщение агента (`reported`), не согласование пользователя.
Обновление checkpoint задаётся процедурой агента; это не доказательство,
что выбранная LLM выполнила её правильно. Исходный transcript сохраняется
независимо от содержания checkpoint.

## Когда происходит сжатие

| Механизм | Настройка | Назначение |
|---|---|---|
| Автоматический OpenCode | `auto: true`, `buffer: "30%"` | Начать сжатие примерно при заполнении 70% известного окна, сохранив запас |
| Недавняя история | `keep.tokens: 6000` | Оставить ближайшие точные реплики рядом со сводкой |
| Регулярный primary | Каждые 8 завершённых ходов | Не ждать большого переполнения при долгой работе |
| Крупные ответы инструментов | 20 000 байт, 320 строк для built-in output; обрезка по первому достигнутому пределу | Ограничить единовременный рост рабочего контекста |

Регулярный запрос отправляется через `ctx.session.compact` на безопасной границе
idle, для `architect` и `orchestrator`, когда нет фоновых заданий. Запрос принимается в
очередь; hook не ожидает завершения модели внутри idle. Счётчик хранится в
storage OpenCode, переживает перезагрузку plugin, учитывает ID последнего ответа
и завершённой compaction, защищён от повторного idle и одновременного вызова.
Один новый последний успешный assistant-ответ на такой границе считается одним
ходом; события при фоновой работе пропускаются и не увеличивают счётчик.

Автоматическое сжатие OpenCode распространяется и на длинные задания субагентов.
Если у модели неизвестен размер окна или неверна его конфигурация, точность
порогов не гарантируется. Нельзя обещать отсутствие любого context-overflow
провайдера: ограничения его токенизатора и fixed prompts остаются внешним
контрактом. Харнесс ограничивает собственную вставку и не пытается продолжить
работу ценой незаметного удаления обязательной памяти.

## Порядок compaction

1. Проверить роль и принадлежность сессии проекту.
2. Получить текущий доступный transcript через OpenCode API и сохранить его
   точный JSON в архив. Если запись не удалась, подготовка сжатия прекращается.
3. Заново прочитать граф и checkpoint. Обязательные ограничения и checkpoint
   сохраняются целиком; если они не помещаются, нужна явная корректировка структуры.
4. Передать модели правила сводки и ID архива, который следует сохранить в сводке.
5. OpenCode записывает summary и оставляет последние 6000 токенов истории.
6. Перед следующим шагом снова загрузить живое состояние. При сомнении открыть
   оригинал по ID. Архив можно найти и без ID в сводке через `list_details(session_id)`.
7. Для `orchestrator` после каждой завершённой compaction заново получить полный
   действующий архитектурный контракт и сверить ТЗ, принятые решения и полномочия
   до зависимого решения, назначения реализации или sign-off. При запрете прямого
   чтения это делает новая сессия worker; длинный текст возвращается частями.
   Plugin добавляет в context/generate напоминание с ID последнего завершённого
   сжатия. Оно не подтверждает фактическое чтение моделью и не создаёт новых прав;
   сводка и прежняя запись evidence не заменяют оригинал. После получения текста
   для этого ID повторное полное чтение на каждом ходе не требуется.

Архив содержит тот transcript, который возвращает API текущей сессии. Ранее
сжатые части остаются в предыдущих архивах и истории OpenCode. Вложения,
двоичные файлы и уже вынесенные OpenCode tool outputs остаются ссылками:
их байты не дублируются в архиве. Доступность внешнего источника требует
сохранения самого источника. Размер одного JSON-архива ограничен 32 MiB;
при превышении операция завершается ошибкой без удаления исходной истории.

## Свежие сессии субагентов

Каждое новое задание создаёт новый child session. Plugin удаляет `sessionID`
из входа инструмента `subagent`, даже если модель попыталась передать его,
и убирает это поле из схемы инструмента для архитектора.

В задание входят только цель, критерий готовности, границы, актуальная ревизия,
ID объектов и ссылки. Размер brief — не более 8000 байт. Старый диалог
не копируется. Каждый помощник получает свежую ограниченную память проекта
тем же hook и может догрузить детали. Помощники не запускают других агентов.

Продолжение — новое задание со ссылкой на предыдущий результат. Для фоновой
работы используются штатные уведомления; повторный вызов со старым sessionID
не служит опросом статуса. Результат помощника краткий (ориентир 1500 токенов),
с точными источниками, условиями проверки и оставшимися неизвестностями.
Родитель сохраняет существенное в графе/свидетельствах и checkpoint.

## Подгрузка по требованию

`get_context(focus=ID)` раскрывает участок; `inspect(ref=ID)` читает точный узел,
связь или предложение. Если результат больше 12 000 байт, MCP возвращает
`paged: true`, ID архива и ключевые метаданные транзакции. Полный результат
уже сохранён; повторять изменение ради полного ответа не нужно.

```text
architect_list_details(session_id="ses_...")
architect_search_detail(detail_id="detail_...", query="нужный идентификатор")
architect_read_detail(detail_id="detail_...", offset=1234, limit=2000)
architect_get_checkpoint(version=3)
```

Offsets измеряются в символах Python, а не в байтах. Следующая страница указана
в `next_offset`; `null` означает конец. Страницы можно соединить и получить
оригинальный JSON; roundtrip-проверка сверяет SHA-256. Поиск буквальный,
регистрозависимый, без исполнения regex или текста архива.

## Бюджет автоматической вставки

Предел по умолчанию — 16 000 байт UTF-8. Если OpenCode сообщает положительные
`limit.context`/`limit.input`, используется меньшее из 16 000 и 12% меньшего
из этих лимитов в байтах. Это осторожная оценка размера вставки, не точный
подсчёт токенов. При выборе полного контекста или индекса учитывается размер
после экранирования `<` и `>`; plugin повторно проверяет размер перед вставкой.

При большом графе сначала исключаются тела свидетельств, длинные описания,
каталог вопросов и подробные связи; вместо них остаётся индекс ID и инструкция
догрузки. Все глобальные ограничения и checkpoint остаются полностью.
Индекс явно указывает количество пропущенных узлов. Если даже обязательная
часть не помещается, запрос останавливается, а данные остаются в хранилище.

Таймаут Python-вызова — 10 секунд. Изменение этих пределов должно сопровождаться
проверкой на выбранной модели и проекте; настройки plugin находятся в `options`.
Очистка архивов — отдельное явное действие оператора с резервной копией, не часть
автоматической compaction.
