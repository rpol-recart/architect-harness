# Агентский харнесс архитектора — v0.3.0 для OpenCode 2.2.5

Проект среды, в которой пользователь и агент постепенно проектируют сложную систему,
ведут архитектурный граф, обсуждают компромиссы и уточняют решения по коду и реальному окружению.

На основе проекта v0.1 реализована интеграция с **OpenCode v2.2.5**: агент-архитектор,
исследователь, аудитор, команды `/arch-*`, MCP и plugin, который читает свежую память
перед обращением к модели, в том числе после инструментов и при сжатии истории.
Цикл модели, диалог и делегирование выполняет OpenCode; граф и его инварианты — Python-ядро.
Субагенты получают отдельные свежие сессии. Основная сессия сжимается с запасом
30% окна и дополнительно каждые 8 завершённых ходов. Checkpoint, точные архивы
и постраничная подгрузка подробностей сохраняют возможность восстановить детали.
Схема графа и методология остались версии 0.1: миграция существующей БД не требуется.

## Запуск в OpenCode

Нужны OpenCode **2.2.5**, Python 3.11+ и настроенная в OpenCode модель с tools.
Проверенное окружение: Linux, Python 3.12.3, MCP SDK 2.3.0. Встроенный JS runtime
OpenCode загружает plugin без npm-зависимостей. Node нужен только для отдельного теста.

```bash
python -m venv .venv
.venv/bin/python -m pip install -e ".[mcp]"
.venv/bin/python -m architect_harness opencode-install . --project-id my-project --title "Мой проект" --profile python
.venv/bin/python -m architect_harness opencode-doctor .
opencode
```

В этой рабочей копии установка уже выполнена с project-id `architect-harness`.
Повторная установка должна использовать этот же ID; другая идентичность проекта
не подменяет существующую память. Для нового проекта выполните установку в другой папке.

В интерфейсе OpenCode:

```text
/arch-start Спроектируем сервис обработки заявок; сначала исследуй существующий код
/arch-focus system
/arch-review change_ID
/arch-resume
```

Установщик добавляет `.opencode/opencode.json` и `.opencode/architect-harness/`,
создаёт пустую `.architecture/architecture.sqlite`, сохраняет сторонние настройки
и отказывается перезаписывать конфликтующие значения. Существующий `default_agent`
в этом конфиге сохраняется; команды `/arch-*` сами выбирают архитектора.
Модель и ключи не добавляются. Необязательный `--model provider/model` закрепляет
модель для трёх ролей; по умолчанию используется выбор OpenCode.

Для другого репозитория передайте его абсолютный путь в `opencode-install`,
затем запускайте OpenCode из того репозитория. Python берётся из активного окружения
установщика, пути записываются абсолютными. После переноса установки пути необходимо
обновить вручную или повторно сгенерировать конфигурацию; изменённые файлы автоматически
не затираются. JSONC в `.opencode/opencode.jsonc` требует ручного объединения до установки.

Подробности ролей, полномочий, рассмотрения diff и проверок — в
[руководстве OpenCode](docs/OPENCODE.md).
Принципы сохранения важного и управления размером контекста — в
[политике контекста](docs/CONTEXT_POLICY.md).

## Быстрый запуск

Ниже — отдельная работа с ядром и универсальным MCP-интерфейсом. Для OpenCode
используйте установку выше: общий `examples/mcp-client.json` не имеет формата V2.

Нужен Python 3.11+. Проверено на Python 3.12; дополнительные версии не проверялись.
Команды ниже выполняются из корня распакованного проекта. В Windows используйте
`.venv\Scripts\python.exe` вместо `.venv/bin/python`.

```bash
python -m venv .venv
.venv/bin/python -m pip install -e ".[mcp]"
.venv/bin/python scripts/demo.py
.venv/bin/python scripts/mcp_roundtrip.py
.venv/bin/python -m unittest discover -s tests -v
```

Для ядра без MCP достаточно `python -m pip install -e .` — оно работает на стандартной библиотеке.
MCP-адаптер рассчитан на официальный SDK `mcp==2.3.0`; он **не является адаптером SDK v1**.
Для воспроизведения использованного набора зависимостей сначала установите
`python -m pip install -r requirements-mcp.lock`, затем `python -m pip install -e .`.

`demo.py` делает настоящий HTTP GET к временному локальному сервису, сохраняет сведения
об ответе и восстанавливает граф через новый экземпляр сервиса. Это демонстрация
транспорта и памяти; она ничего не доказывает о production API.

`mcp_roundtrip.py` поднимает сервер отдельным процессом и использует официальный клиент:
обнаружение инструментов, контекст, предложение изменения, отказ без полномочий,
разрешение со стороны host, применение, повтор запроса и запись сообщения клиента.
Сообщение `review_required` в этом сценарии ожидаемо; итоговый результат — `success: true`.

## Создание собственного графа

```bash
.venv/bin/python -m architect_harness --db architecture.sqlite init --project-id my-project --title "Мой проект"
.venv/bin/python -m architect_harness --db architecture.sqlite propose examples/bootstrap.json
```

`bootstrap.json` описывает сам харнесс и служит примером формы данных. Для собственного
проекта замените окружение и сценарии на реальные. Начальный граф пустой, ревизия — 0.
Команда `propose` возвращает ID предложения, diff и причины необходимого рассмотрения.

Пользователь/доверенный host рассматривает конкретный diff. Вместо `CHANGE_ID` подставьте
ID из результата `propose`:

```bash
.venv/bin/python -m architect_harness --db architecture.sqlite show-change CHANGE_ID
.venv/bin/python -m architect_harness --db architecture.sqlite approve CHANGE_ID --revision 0 --reviewer "Владелец проекта"
.venv/bin/python -m architect_harness --db architecture.sqlite apply CHANGE_ID --revision 0
.venv/bin/python -m architect_harness --db architecture.sqlite context --focus system --profile core --profile python
.venv/bin/python -m architect_harness --db architecture.sqlite mermaid
```

Просмотр lifecycle и отмена неприменённого предложения оператором
([ADR-009](docs/DECISIONS.md#adr-009-терминальный-lifecycle-предложений-без-переписывания-истории)):

```bash
/absolute/path/.venv/bin/python -m architect_harness --db /absolute/path/architecture.sqlite list-changes
/absolute/path/.venv/bin/python -m architect_harness --db /absolute/path/architecture.sqlite cancel CHANGE_ID --revision N --reviewer "Владелец проекта"
```

Замените абсолютные пути и `CHANGE_ID`; `N` — текущая ревизия из заголовка
`list-changes`. Команда чтения показывает id, payload- и эффективный статус,
base/applied_revision, время создания и автора. Отмена не удаляет предложение и
не меняет граф: append-only событие делает его `cancelled`, запрещая approve/apply.
`cancel`, как и `approve`, отсутствует в MCP. Optional `supersedes` у MCP
`propose_change` связывает замену с прежним предложением; цель становится
`superseded` только после операторского approve и успешного apply замены.

Согласование требуется для существенных изменений согласно политике. Локальное изменение,
которое не затрагивает защищённые элементы, применяется без отдельного согласования.
`approve` отсутствует среди MCP tools. Это граница интерфейса, **не OS sandbox**:
агент с доступом к тому же shell/SQLite сможет обойти её. Для более сильной изоляции
host должен разделять полномочия и каналы исполнения.

## Подключение MCP host

Сначала создайте БД и установите пакет в окружение, затем адаптируйте
[пример конфигурации клиента](examples/mcp-client.json): замените оба абсолютных пути.
Формат конфигурации конкретного host может отличаться.

```bash
.venv/bin/python -m architect_harness --db /absolute/path/architecture.sqlite serve
```

Сервер работает через stdio. Он не открывает HTTP-порт. Не запускайте эту команду
как обычную интерактивную оболочку: stdin/stdout используются протоколом.

В начале архитектурной сессии host должен получить `get_methodology`, затем `get_context`.
Одно наличие MCP resources не гарантирует, что host включит их в контекст модели.
`architect-workflow.md` — версия рабочего скилла **этого приложения**; пакет не устанавливает
персональный скилл ChatGPT и не меняет настройки вашего клиента.

| Tool | Назначение |
|---|---|
| `get_methodology` | Рабочая процедура и онтология |
| `get_context` | Подграф, общие ограничения, вопросы и сведения о пропущенных данных |
| `inspect` | Узел, связь или предложение по ID |
| `propose_change` | Подготовка неизменяемого пакета изменений |
| `apply_change` | Атомарное применение с проверкой ревизии и полномочий |
| `record_observation` | Сообщение агента с provenance=`reported` |
| `save_checkpoint` / `get_checkpoint` | Версионируемый краткий handoff: цель, требования, решения, работа и ссылки |
| `list_details` / `search_detail` / `read_detail` | Найти точные архивы и прочитать нужный фрагмент |

Результат MCP больше 12 000 байт сохраняется целиком и возвращает `paged: true`,
`detail_id` и метаданные операции. Читайте его через `read_detail`, используя
`next_offset`; для нужного места используйте `search_detail`. Это касается также
методологии и подробного diff. Результат операции уже сохранён независимо от
того, полностью ли прочитан ответ. `scripts/mcp_roundtrip.py` показывает обработку страниц.

В `get_context` лимит узлов мягкий: общие ограничения и существенный связанный контекст
могут увеличить ответ. Превышение и пропуски обозначаются явно; строгого token budget пока нет.
Повтор `apply_change` возвращает исходный снимок результата, даже если граф уже изменился.
После повтора получите актуальное состояние через `get_context`.

## Исследование реального окружения

Статический просмотр настоящего Python-проекта:

```bash
.venv/bin/python -m architect_harness inspect-python ./src
```

Команда не импортирует и не исполняет исследуемый код. Она возвращает импорты,
разрешимые зависимости и эвристические признаки потенциальных проблем. Динамическое
поведение и корректность бизнес-правил из такого отчёта не следуют.

Наблюдение HTTP выполняет оператор, явно задавая разрешённый origin и существующий узел:

```bash
.venv/bin/python -m architect_harness --db architecture.sqlite probe-http https://your-service.example/health --allow-origin https://your-service.example --related host
```

Адрес выше — placeholder, его нужно заменить доступным реальным endpoint. Сохраняются
код ответа, длительность, длина и хеш ограниченного тела; само тело не сохраняется.
Переходы не выполняются. Отсутствуют авторизация, записи в API и универсальный сетевой MCP tool.
Socket timeout ограничивает отдельное ожидание; общего дедлайна всей передачи пока нет.
Наблюдение доступности не подтверждает бизнес-контракт, идемпотентность и производительность.

Сообщение об исследовании можно внести через `observe FILE.json` по форме
[examples/observation.json](examples/observation.json). Оно останется `reported`;
сервер не выдаёт сообщение модели за самостоятельно выполненное действие.

## Что обеспечивает v0.1

- Версионирование графа и журнал событий в SQLite.
- Атомарные изменения, обнаружение устаревших предложений, повтор применения без дублирования.
- Отдельные статусы решений, утверждений и вопросов.
- Неизменяемые свидетельства и происхождение записи.
- Отсутствие висячих связей, циклов `contains`, двух владельцев одного набора данных.
- Машинное правило `forbid_dependency` для прямых связей `depends_on` / `interacts_with`.
- Выдача релевантных вопросов по типам узлов и объявленным тегам.

Правило запрета не анализирует транзитивные пути и код; человеческие текстовые ограничения
сохраняются как контекст. Наблюдение не закрывает вопрос и не принимает решение автоматически.
Исходные связи свидетельства тоже неизменяемы: узел, на который уже ссылается наблюдение,
сохраняется как исторический объект. Физически удалить его через graph API нельзя.
Возврат вопросов на пересмотр после изменений описан в проекте; автоматический dependency-based
invalidation пока не реализован. Изменённые гипотезы пересматривает агент по рабочей процедуре.

## Границы ядра и интеграции

Нет визуального редактора, remote authentication, multi-tenancy, собственного LLM-планировщика,
контроля любых shell/file-инструментов и автоматического утверждения семантической правильности.
OpenCode выполняет агентский цикл и применяет разрешения настроенных ролей. Это не
OS sandbox: другой агент, прямой shell или процесс с доступом к SQLite могут обойти эту границу.
SQLite-файл — одно локальное доверенное рабочее пространство. Секреты и полные production-ответы
не следует помещать в граф. Выполнение проверок ядра не является доказательством пригодности
архитектуры для конкретного пользовательского проекта.
Каждая ревизия хранит полный JSON-снимок, а контекст строится по снимку в памяти. Масштабирование
на большие графы и длительную историю ещё не измерялось; понадобится отдельная оценка.

Следующая приёмка — один настоящий проект пользователя: восстановить окружение, исследовать
значимую интеграцию, обсудить компромисс, сохранить его основания и продолжить работу в новой сессии.

## Проверка v0.2

```bash
.venv/bin/python -m unittest discover -s tests -v
node --test tests/opencode-plugin.test.mjs
.venv/bin/python scripts/mcp_roundtrip.py
.venv/bin/python scripts/opencode_smoke.py --output reports/opencode-smoke.json
```

JS-тест использует `python3` из PATH с установленным пакетом; для другого
интерпретатора задайте `HARNESS_PYTHON=.venv/bin/python node --test tests/opencode-plugin.test.mjs`.

Последняя команда создаёт временный проект и отдельный настоящий сервер OpenCode;
не меняет глобальные настройки, не использует ключи провайдеров и не вызывает LLM.
Пределы каждой проверки записываются в отчёте. Исходные отчёты v0.1 сохранены как
история исходной поставки; актуальные результаты перечислены в `reports/verification-v0.2.json`.
